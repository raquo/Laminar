## Laminar updates

### MathML support

In addition to HTML and SVG you can now build [MathML](https://developer.mozilla.org/en-US/docs/Web/MathML) elements in Laminar:

```scala
import com.raquo.laminar.api.L.mathml._

mathTag(
  mi("E"), mo("="), mi("m"), msup(mi("c"), mn(2))
)
```

Result:   (#TODO: check that website renders this)

#TODO: Add link to larger example in the demo project

<math>
  <mi>E</mi><mo>=</mo><mi>m</mi><msup><mi>c</mi><mn>2</mn></msup>
</math>

MathML supports all Laminar features – styling with CSS props, `<--` and `-->` bindings, click events etc. There are now also MathML versions of external integration methods: `unsafeParseMathMlString` and `foreignMathMlElement`.

MathML elements / attributes / classes were added to [Scala DOM Types](https://github.com/raquo/scala-dom-types) and [scala-js-dom](https://github.com/scala-js/scala-js-dom) by **[@Quafadas](https://github.com/Quafadas) – thanks!**


### Pipe the same input into multiple modifiers

The new `modSeqWith` method returns a Seq of modifiers, each of which is created from the same `input`. [#146](https://github.com/raquo/Laminar/issues/146)

This is convenient when you want to bind multiple listeners to the same observable without repeating yourself:

```scala
div(
  modSeqWith(coordinatesSignal.map(process).distinct)(
    left.px <-- _.map(_.x),
    top.px <-- _.map(_.y),
    _.map(_.z) --> zObserver
  )
)
```

The above is equivalent to the more verbose and error-prone:

```scala
lazy val coords = coordinatesSignal.map(process).distinct
div(
  left.px <-- coords.map(_.x),
  top.px <-- coords.map(_.y),
  coords.map(_.z) --> zObserver
)
```

There is also `seqWith` for a more generalized version that is not tied to Modifiers, but its type inference does not play well with Modifier implicit conversions, so use `modSeqWith` for creating modifiers.


### Boolean toggle methods

You can now conditionally apply any attribute / property with a similar syntax to what Laminar has already offered for the `cls` attribute:

```scala
val shouldHighlight: Boolean = ???
val shouldHighlightS: Signal[Boolean] = ???
val shouldHide: Boolean = ???
val shouldHideS: Signal[Boolean] = ???

// We already had this available for `cls` pre-v18:
cls("highlighted") := shouldHighlight
cls("highlighted") <-- shouldHighlightS

// Applies background color only when shouldHighlightS emits true.
// When false, the background-color property is unset.
backgroundColor("#ff9900") <-- shouldHighlightS

// Similarly, applies display.none conditionally
display.none <-- shouldHideS

// Applies display.none only when shouldHide is true,
// unset the display property otherwise.
display.none(shouldHide)

// Remember that `:=` and `apply` are aliases in Laminar element-building APIs, so these work all the same:
(backgroundColor := "#ff9900")(shouldHighlight) 
backgroundColor("#ff9900") := shouldHighlight
backgroundColor("#ff9900")(shouldHighlight)
```

Note that unlike the existing `when(shouldHighlight)(backgroundColor("#ff9900"))` syntax, this new syntax actively unsets the attribute/property value when a `false` boolean value is provided. This makes it useful to subscribe to observables of booleans with the new syntax.


### Improved `attr.maybe` API and behaviour

Previously, `attr.maybe(valueOption)` would set value if provided `Some(value)`, and would do nothing if provided a `None`. Now, in line with boolean toggle methods above, it actively unsets the attribute's value if provided a `None`. Also, we've added the `attr.maybe := valueOption` and `attr.maybe <-- optionObservable` methods match the rest of the Laminar's API.

This is available on all attrs, props, style props.

**Migration:** if you need to retain existing behaviour, replace usages of `attr.maybe(valueOption)` with `valueOption.map(attr := _)`.


### New type hierarchy for keys (attrs / props / etc.)

Laminar's primary element-building API is still the same, but internally quite a few types have been renamed, rearranged, their contracts adjusted to make them more principled and a bit safer.

You can now abstract over these types easier, e.g. you can write a method that accepts any kind of Laminar key and work with it effectively, e.g. use its `<--` method in a type safe way.

- `HtmlProp[V, DomV]` is now just `HtmlProp[V]` as `DomV` is basically never needed in user code. It is still available as `DomV` type member on `HtmlProp`.
- You now need to provide a type param when creating custom CSS props, e.g. `styleProp[String]("gap")`. If the type param is not String, it should be an `A | String` union type if you want the ability to pass standard CSS strings to it (such as `"none"` / `"inherit"` / etc.) in addition to `A` values.
- API: Moved global attrs into `GlobalAttr`-s and `ComplexGlobalKeys` (e.g. `idAttr`, `tabIndex`, `cls`, `role`, `dataAttr()`.)
  - These attrs can now be used on any instance of HTML, SVG, MathML regardless of where you imported the attr from (e.g. `cls` and `svg.cls` are interchangeable).
  - You can create a custom ones with `globalAttr(name, codec)`
- More internal changes:
  - **Migration:** There are too many internal changes to list them individually. The intended public API is mostly the same as before (aside from the above), but the names and hierarchies of the types implementing it have changed, so if you referenced the types themeselves in your code, you may need to adjust these references to rename them, correct the type params, etc. Some types offer migration guidance via `@deprecated` warnings. In my own Laminar codebases the number of changes needed was very small.
  - See the new types and their scaladoc & type hierarchies:
  - `SimpleKey`, `SimpleKeySetter`, `SimpleKeyUpdater`, `CompositeKey`, `CompositeKeySetter`, `CompositeKeyUpdater` etc.
  - See the traits that `object DomApi` extends
  - Split off `DerivedStyleBuilder` from `StyleBuilder`


### New small Laminar features
- Added `element.select()`, which selects the entire contents of the element, the way the browser lets you select text on a web page. If it's an `input` or a `textarea` element, we also focus on it.
- Added `onMountSelect`, which runs `element.select()` (see above) on mount.
- Added `text.maybe <-- ` which accepts `Signal[Option[TextLike]]` where `TextLike` includes strings, numbers, booleans, and any `V` with a `RenderableText[V]`.
- In Scala 3, you can now directly render `if (...) “str” else 5` without needing to explicitly wrap both into `TextNode`. Works in `text <--` too.
- Added `debugLogLifecycle(label = "")` modifier – adding it to an element will print out mount and unmount events of that element in the console.
- Reworked Laminar's implicits. If you have e.g. `HtmlAttr[A]` and `EventStream[B]`, you can now say `attr <-- stream` as long as an implicit conversion from `A` to `B` is in scope. This is done efficiently without creating a new observable.
-  [CSS var / custom property](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascading_variables/Using_custom_properties) helper added, with the same API as other CSS units like `px`:
  - `backgroundColor.cssVar("--my-bg-color")` sets the `background-color` property to `var(--my-bg-color)`
  - you're then supposed to define the variable `--my-bg-color` in your CSS file, possibly switching it based on theme etc. 
- CSS props are now allowed on SVG root elements, and MathML elements too
- WebComponent-s
  - Added `partAttr` and `exportParts` composite attrs for web components (Laminar only)
  - Added `slotTag`
- Added `fontFeatureSettings.tnum` keyword and a few other keys in [Scala DOM Types](https://github.com/raquo/scala-dom-types/blob/master/CHANGELOG.md).

### Minor Laminar behaviour changes
- API: Run `onMount*` callbacks if adding `onMount*` block to an element **that has already been mounted**. [#149](https://github.com/raquo/Laminar/issues/149).
    - Previously, the mount callbacks would not run in this edge case, resulting in a hidden assumption about the current state of the element to which you're adding the modifier.
    - This is only relevant to advanced user code that adds `onMount*` modifiers to an element at some point **after** said element was created. The behaviour of simple `div(onMountCallback(...), ...)` is unchanged.
    - **Migration:** You can get the previous behaviour by passing `ignoreAlreadyMounted = true`
    - `onMountFocus` does not support `ignoreAlreadyMounted = true`, but you can write such a helper manually if needed.
    - `onMountUnmountCallbackWithState` now provides the state as `A` instead of `Option[A]` by default, because the new default behaviour makes that safe.
    - Otherwise, the Unmount callbacks are unaffected. `onUnmountCallback` is unchanged – it still won't run if you add an `onUnmountCallback` block to an already-unmounted element. It only runs when the element is actually being unmounted.
- Fix: Use lazy evaluation for arguments of `when` and `whenNot`, i.e. `when(condition)(content)` will evaluate `content` only if `condition` is true. This brings consistency with the rest of the universe. [#169](https://github.com/raquo/Laminar/issues/169). **Thanks, [@neunzehnhundert97](https://github.com/neunzehnhundert97)!**
    - **Migration:** Scala 2 does not support varargs, so the vararg versions of these methods are only available in Scala 3 now. In scala 2, you'll now need to wrap the vararg contents in `modSeq()`.
    - **Migration:** To retain previous strict behaviour (for some odd reason), save the contents in a `val` before rendering.
- Fix: `renderOnDomContentLoaded` now runs the callback even if we missed the `DomContentLoaded` event. [#175](https://github.com/raquo/Laminar/issues/175) **Thanks, [@sjrd](https://github.com/sjrd)!**
  - **Migration:** You're not affected unless you have implemented a workaround for this in your code. In that case, remove your workaround.

Otherwise, you won't be notified of these issues, as before.

  - Fixed `ChildCommandInserter` not ensuring strict mode

### Fixes in foreign* and unsafe* APIs
- (Note: The security concerns of calling `unsafe*` APIs on untrusted input have not changed. It's still as unsafe as ever.)
- Fix the contract of `foreignHtmlElement(tag, element)` and `foreignSvgElement(tag, element)`
  - These methods now accept any element as originally intended, and do a robust runtime checks to ensure that the element matches the provided tag.
  - Previous version only accepted element types that already match the element, which is inconvenient and unnecessary.
  - We swapped the order of `(element, assertTag)` params when calling (`tag` is last now)
  - The new version of the method will throw if the element does not match (as originally intended).
  - **Migration:** to avoid throwing, you can use `foreignHtmlElement` / `foreignSvgElement` without the `tag` argument.
- Change the order of arguments
  - in `foreignHtmlElement` and `foreignSvgElement` – tag goes last now
  - in `unsafeParseHtmlString` and `unsafeParseSvgString` – tag goes last now
    - Previously, we were getting misleading compiler error messages if the types don’t match
- The `unsafeParseHtmlString` and `unsafeParseSvgString` methods now trim the input string.
  - Previously, extraneous whitespace would cause these to fail single-node assertion.


### Misc breaking changes
- API: Remove `child(el) <-- signalOfBooleans`, `child(el) := true`, and `child(el)(true)` syntax – yes, `child` is the Laminar keyword in those snippets.
  - I don't think these were carrying their weight – just one more way to do the same thing, and a weird one at that. Among other issues, the (lack of) laziness in evaluating the content is undesirable. Eventually I will expand `when` / `whenNot` syntax to cover these use cases. For now, you'll have to use regular Laminar syntax for this.
- API: Numeric style props now return `Double | Int` type if you **read** their value, e.g. `flexGrow(2).value` is `Double | Int`.
  - This isn't desirable on its own, but it makes it easier to _write_ both `Int` and `Double` values into such props without manual conversion and without sacrificing type safety. And we do a lot more writing than reading in typical Laminar code.
- API: `htmlProp(name, reflectedAttrName, codec)` factory method for custom HTML props now accepts the second `reflectedAttrName` argument. See SDT docs on [[reflected attributes]]( [[https://github.com/raquo/scala-dom-types?tab=readme-ov-file#reflected-attributes About reflected attributes]]). If unsure, you can provide `None`. If you got it wrong, `yourCustomProp.maybe` may not work properly at runtime.
- Refactor: Reworked Laminar's implicits internally. This should have no consequences, but if you manually referenced a specific implicit, it may have been moved / removed / reorganized.
- Moved to new locations:
  - `CompositeCodec`, `CompositeValueMapper`
  - `CompositeKey.normalize` -> `CompositeCodec.normalize`
  - `Codecs`
    - `StringAsIsCodec` -> `Codec.stringAsIs` and so on
    - Deprecation warnings suggest migration.
  - `SvgAttr.{namespaceUri, *namespaceUri}` -> `DomApi.*`
    - Deprecation warnings suggest migration.
  - `CompositeValueMappers` -> `CompositeValue.Implicits`
  - `child.text` -> `text`
    - Deprecation warnings suggest migration.


## Airstream updates

### Airstream API cleanup & upgrades – split, strict signals, etc.


#### Changes to `split*` operators

- Old `split` operator is deprecated in favor of `splitSeq`
  - `splitSeq` works the same as `split`, but provides a single `KeyedStrictSignal` instead of `(key, initial, signal)`
  - You can get `.key` and `.now()` from this new signal to get `key` and `initial`:
    ```scala
    // Before:
    itemsSignal.split(_.id) { (itemId, initialItem, itemSignal) =>
      div(
        cls(s"item-${itemId}"),
       "initial=", initialItem.name, "; ",
       text <-- itemSignal.map(_.name)
      )
    }
    // Now:
    itemsSignal.splitSeq(_.id) { itemSignal =>
      div(
        cls(s"item-${itemSignal.key}"),
       "initial=", itemSignal.now().name, "; ",
       text <-- itemSignal.map(_.name)
      )
    }
    // Or, if you want to name the ID meaningfully:
    itemsSignal.splitSeq(_.id) { case itemSignal withKey itemId =>
      div(
        cls(s"item-${itemId}"), // `itemId` instead of `itemSignal.key`
       "initial=", itemSignal.now().name, "; ",
       text <-- itemSignal.map(_.name)
      )
    }
    // Alternative syntax:
    itemsSignal.splitSeq(_.id) { case withKey(itemSignal, itemId) =>
      // same as above
    }
    ```
  - Note: `.now()` is the signal's live-updating current value. You can say `val initial = modelSignal.now()` inside the `splitSeq` callback if you need to lock down the initial value.
  - You can use the new `withKey` helper to meaningfully name the itemId variable instead of referring to `key`.
    - Note: when splitting Var-s, use `varWithKey` instead.
  - The API of other `split*` operators has been updated in the new `splitSeq` style – one `StrictSignal` argument instead of `(initial, signal)`, for example:
    ```scala
      // Before:
      itemOptionSignal.splitOption { (initialItem, itemSignal) =>
        ...
      }
      // Now:
      itemOptionSignal.splitOption { itemSignal =>
        val initialItem = itemSignal.now()
        ...
      }
      ```
  - `distinctCompose`
    - `distinctCompose` argument was renamed to `distinctOp` (except in the original, now-deprecated `split`), and now accepts only `.distinct*` operators. It also accepts the `identity` function as a shorthand for `distinctByFn(isSame = (_, _) => false)`. Arbitrary operators are not allowed anymore (that was never the intent).
- New split operator variations:
  - `splitSomeSeq`, `splitSomeSeqByIndex` – for observables of `Option[Seq[A]]`
- Generalize some split variations:
  - For example, `splitOne` was only available on Signals and on EventStream-s, but not on their supertype `Observable`. Now, we have a universal `splitOne` implementation on `Observable` that works just as well as before, plus works on Observable instances, when you don't know if it's a signal or a stream.
  - We did the same for split operators in `BooleanSignal`, `EitherSignal`, `TrySignal`, `StatusSignal`
  - **Migration:** We removed `OptionSignal`, `BooleanSignal`, `EitherSignal`, `TrySignal` value classes – if you accidentally imported them, just remove the import, all their functionality is still there in similarly named `*Observable` classes.
  - Naming: `stream.splitBoolean` arguments renamed from `trueF` / `falseF` to `whenTrue` / `whenFalse`.  **Migration**


#### Changes to handleCase & handleType

- `handleCase` and `handleType` have a similar shape to `split` operators, and were also updated to change their callback from `(initialItem, itemSignal) => ...` to just one `itemSignal` argument that exposes its current value via `.now()`.


#### Var.zoom does not require an owner anymore

- Background: Up to and including v17.0.0, you could only `zoom` into a `Var` if you provided an `Owner`. In v17.1.0 we [introduced](https://laminar.dev/blog/2024/08/14/laminar-v17.1.0#zoom-into-a-var-without-needing-an-owner) a new `zoomLazy` method that does not need an `Owner`, with the intent of making that behaviour the default in the next major version.
- The time has cometh! As of v18.0.0, `zoom` is now lazy, and does not require an `Owner`. Use it!
- The old version of `zoom` that requires an `Owner` is now available as `zoomStrict` – you can still use that to simplify **Migration**.


#### Strict signal operators now return LazyStrictSignal-s

- Previously, `strictSignal.map` returned a regular, lazy, non-strict Signal. It was hard to create derived `StrictSignal`-s derived from other `StrictSignal`-s.
- Most [flowy](https://github.com/raquo/airstream/#flowy-operators) `StrictSignal` operators (`map`, `distinct`, `scanLeft`, `recover`, `debugLog`, and their variations) now return a `LazyStrictSignal` instead of regular Signal.
- `LazyStrictSignal` is basically the equivalent of `LazyDerivedVar` aka the new `Var.zoom`.
- `LazyStrictSignal` exposes a public `.now()` method like any other `StrictSignal`, however its semantics are lazy like regular signals:
  - It will not evaluate its value unless and until it's needed (for your `.now()` call, or if it has observers).
  - When you call `.now()`, it will pull a fresh value from its parent signal if needed (e.g. if it has no observers and has not been keeping up with the parent signal)
    - Remember that signals can't pull values from parent streams, only from parent signals.
  - It will compute its value at most once per parent signal update.
- **Note:** Parent events on signals that have no observers can be missed, for example:
  - If you have `strictSignal.distinct*` and don’t subscribe to the resulting signal, the distinct comparator will only run when you call `.now()`, even if the parent `strictSignal` updates multiple times between your `.now()` calls.
  - Similarly, if you have `strictSignal.scanLeft*` and don’t subscribe to the resulting signal, the accumulating callback will only run when you call `.now()`, even if the parent `strictSignal` updates multiple times between your `.now()` calls.
  - To get every update in such cases, you need to subscribe to such signals. Don't abuse the ability to pull values with `.now()` if your actual logic should be push-based.
- **Note:** A `StrictSignal` firing an error value while having no observers no longer triggers an Airstream unhandled error.
  - Previously this was an edge case that we thought should be reported this way, but now that we’re normalizing the use of `LazyStrictSignal` without requiring subscribers, this situation is potentially quite routine, and does not warrant a warning.
- **Migration:**
    - Existing uses of `strictSignal.map` etc. should be unaffected.
- [`strictSignal.mapLazy`](https://laminar.dev/blog/2024/12/13/laminar-v17.2.0#mapping-strictsignal-s) was deprecated – just use `strictSignal.map` it behaves the same now.

### Other new features in Airstream
- **`Signal.toStream`**
  - works like `signal.changes` (aka `signal.updates`), except it also emits the signal's current value on first startup. It is useful if you wish to explicitly trade Signal's current-value semantics for EventStream's richer functionality (incl. filtering and async methods). This new method is somewhat experimental, and its exact behaviour may see subtle refinements in the future. Fixes [#124](https://github.com/raquo/Airstream/issues/124)
- New type-specific operators
  - Observable[Boolean]
    - `mapTrueToSome(value)`, `mapFalseToSome(value)` – **Thanks, [@cheleb](https://github.com/cheleb)!**
    - `mapTrueToSeq(seq)`, `mapFalseToSeq(seq)`
  - Observable[Option]
    - `mapSomeToOption`, `mapSomeToSeq`
    - `someOrElse(ifEmpty)`
  - Observable[Try]
    - `successOrElse(err => value)`
  - Observable[Either]
    - `rightOrElse(ifLeft)`, `leftOrElse(ifRight)`
  - Observable[Seq]
    - `mapSeq(projectValue)`, `seqOrElse(ifEmpty)`
  - Observable[Option[Seq]]
    - `mapSeqOpt(projectValue)`,
    - `seqOptOrElse(ifEmptySeq)`
    - `seqOrElse(ifEmptySeq, ifNone)`
- `EventStream.dynamicImport(resource)` and `stream.dynamicImport(ev => resource)` operators (and similar ones for signals) – these load `resource` with [JS dynamic imports / module splitting](https://www.scala-js.org/doc/project/module.html#dynamic-imports), i.e. bundlers like Vite will download the compiled code that is needed to execute `resource` on-demand only, without including it into the initial JS bundle download.
  - This will be effective to the extent that the types / classes / functions / values used in `resource` are not already used elsewhere in your app. You can thus reduce generated bundle size by hiding heavy and/or rarely used features of your application behind .dynamicImport.
  - These streams emit asynchronously once the download is complete, and provide the executed `resource`.
  - Fixes [Waypoint#24](https://github.com/raquo/Waypoint/issues/24). **Thanks, [@elgca](https://github.com/elgca)!**



### Other small Airstream features and changes
- **Migration:** should be obvious if needed, or as noted.
- API: `{Signal,EventStream}.{fromFuture,fromJsPromise}` now evaluate their future / promise **lazily**, only once the signal / stream is actually started. They still evaluate it only once, on the first start. Previous behaviour was strict evaluation.
- API: `EventStream.delay(ms = 100, event)` now evaluates the event by-name, only when emitting it.
  - **Migration:** rewrite to `EventStream.fromValue(event).delay(100)` to maintain previous behaviour.
- API: Rename `Signal.changes` method to `signal.updates`:
    - `changes`, `changes(op)`, `composeChanges` → all renamed to `*updates`
- New: `debugLogAll`, `debugSpyAll` operators
  - **Migration:** also, renamed some arguments to debug operators
- New: `tapEachError` operator
- New: `matchStreamOrSignalAsSelf` operator
  - Similar to `matchStreamOrSignal`, but guarantees that the return is of type `Self[B]` within `BaseObservable[Self, A]`. Can be useful for solving some typing issues with highly generic code.
- API: Generate N-arity helpers for arity up to 22 (previously was up to 9) – `combineWith` / `withCurrentValueOf` / `sample` etc. are available in up to 22-observable versions out of the box now.
    - **Migration:** 
      - If you previously replaced `tuplez-full-light` dependency in your build with `tuplez-full` to achieve this, you should remove that override.
      - If you combined more than 9 items using these methods, you had to deal with the first 9 items being nested in a separate tuple from the rest. Now, airstream flattens all that into a single tuple (up to 22 items), so you need to adjust your code to expect one flat tuple.
- Fix: Privatize constructor params of (implicit) value classes.
  - **Migration:** you might have inadvertently accessed e.g. `mySignal.signal` which returns the same `mySignal`. This `val` being exposed was not intentional, so access to it is now removed. If you see usages of `.signal`, `.stream`, `.observable`, or `.v` that are not found in v18, you should just remove this call and use the original signal / stream / observable / var directly.
- API: If the signal’s initial value is an error and we try to filter it out with e.g. `signal.recoverIgnoreErrors`, we can’t filter it out, because Signal _needs_ to have _some_ initial value, even if it's an error value. So, pre-v18 we would just use the error as the initial value as-is, despite the request to ignore (skip) the error. Now in v18, we wrap such an error in `InitialValueError` to indicate the reason why we're emitting it. This `recoverIgnoreErrors` wart will need better handling in the future...
